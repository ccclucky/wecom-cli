# WeCom CLI 接口覆盖项目 PRD（v1）

## 1. 背景与目标

本项目目标是为 WeCom CLI 建立一套可执行、可度量的“全量公开接口覆盖”能力，确保对外公开接口在 v1 阶段具备可用、稳定、易维护的调用支持，并通过标准化文档降低接入成本。

---

## 2. 目标用户（Target Users）

1. **内部开发者（SDK/CLI 维护者）**
   - 关注接口实现进度、覆盖率、回归稳定性与发布质量。
2. **业务开发者（CLI 使用者）**
   - 通过命令行快速完成接口调用、调试与脚本化集成。
3. **测试与质量保障人员**
   - 基于统一口径验证接口覆盖、异常处理与稳定性。
4. **技术文档维护者**
   - 维护命令说明、示例与变更记录，保障对外可读性。

---

## 3. 核心场景（Core Scenarios）

1. **接口能力验证**
   - 维护者希望快速确认“某公开接口是否已支持、如何调用、是否通过自动化校验”。
2. **业务脚本集成**
   - 使用者希望以统一命令参数风格调用接口，并能稳定用于 CI/CD 或日常运维脚本。
3. **回归与发布检查**
   - 测试人员希望在发版前拿到覆盖率、失败清单、稳定性统计，形成准入依据。
4. **问题定位与自助排查**
   - 使用者希望根据 CLI 错误信息和文档在 5 分钟内定位常见问题。

---

## 4. v1 范围（In Scope）

### 4.1 能力范围

1. 建立并冻结 v1 的**公开接口清单基线**（API Baseline）。
2. 为清单内接口提供对应 CLI 命令支持（含必要参数与响应输出）。
3. 提供覆盖率统计脚本/流程，输出可追踪报表。
4. 提供基础稳定性验证（成功率、重试策略有效性、错误码可识别）。
5. 提供最小完整文档集（安装、鉴权、命令用法、示例、常见错误）。

### 4.2 交付物

- PRD 文档（本文件）
- v1 公开接口基线清单
- 覆盖率统计方法与结果模板
- 验收 checklist（覆盖率、稳定性、易用性、文档完整性）

---

## 5. 非目标（Out of Scope / Non-goals）

1. 不包含未公开、灰度、内部专用接口的支持与承诺。
2. 不在 v1 承诺跨语言 SDK 的统一实现，仅聚焦 CLI 能力。
3. 不在 v1 引入复杂可视化平台（如 Web 控制台）；仅提供命令行与文档。
4. 不在 v1 保证所有高级特性（如批量编排、插件生态）。

---

## 6. “全量公开接口覆盖”口径与统计方法

### 6.1 口径定义

“全量公开接口覆盖（v1）”定义为：

> 在 **v1 基线日期** 已对外公开且可调用的接口集合中，CLI 已提供可执行命令并通过对应自动化验证的接口占比。

其中：
- **公开接口**：以官方文档/开放平台目录中标记为公开可用为准。
- **接口基线**：在 PRD 评审通过后锁定版本（含接口 ID、名称、分组、状态）。
- **已覆盖接口**：同时满足以下条件：
  1) CLI 中存在对应命令入口；
  2) 参数校验与鉴权流程可运行；
  3) 自动化测试（正向用例至少 1 条）通过；
  4) 文档中有可执行示例。

### 6.2 统计方法

设：
- `N_total` = v1 基线中的公开接口总数
- `N_covered` = 满足“已覆盖接口”定义的接口数
- `Coverage` = `N_covered / N_total * 100%`

#### 统计规则

1. 统计粒度以“接口”为单位（不是命令子参数组合）。
2. 同一接口多命令别名仅计 1 个覆盖项。
3. 依赖外部条件导致长期不可测的接口，必须进入“豁免清单”，并从分母剔除后单独披露：
   - `N_effective_total = N_total - N_exempt`
   - `Coverage_effective = N_covered / N_effective_total * 100%`
4. 每次里程碑输出两份数据：
   - 原始覆盖率（含全部基线）
   - 有效覆盖率（扣除豁免项）
5. 所有统计结果需附带清单明细（覆盖/未覆盖/豁免原因）。

---

## 7. 验收标准（Acceptance Criteria）

### 7.1 覆盖率

1. **有效覆盖率 `Coverage_effective >= 95%`**。
2. 关键高频接口（按优先级 P0 清单）覆盖率 **100%**。
3. 未覆盖项必须有明确计划（负责人 + 截止日期）。

### 7.2 稳定性

1. 自动化回归中，已覆盖接口用例整体通过率 **>= 99%**（按最近连续 7 天统计）。
2. 对可重试错误具备统一重试策略，且失败日志包含可定位信息（错误码/请求标识）。
3. 不允许存在阻断级缺陷（P0）进入发布。

### 7.3 易用性

1. 新用户按文档完成首次成功调用时间（TTFS）**<= 30 分钟**。
2. CLI 命令帮助信息完整（参数说明、示例、错误提示）。
3. 常见错误场景具备可操作的修复建议（至少覆盖 Top 10）。

### 7.4 文档完整性

1. 文档至少包含：安装、配置、鉴权、命令总览、分接口示例、FAQ、故障排查。
2. 每个已覆盖接口必须提供：
   - 最小可运行示例
   - 参数说明
   - 返回示例
   - 错误处理说明
3. 发布前文档可用性检查通过（链接有效、示例可执行、版本标记一致）。

---

## 8. 阶段门禁（Stage Gate）

- **必须先完成 PRD 评审并明确通过结论，才可进入开发阶段。**
- 评审通过的最小条件：
  1. 目标用户与场景达成一致；
  2. v1 范围与非目标边界明确；
  3. 覆盖口径与统计方法冻结；
  4. 验收标准可测量、可执行。

---

## 9. 成功指标（Success Metrics）

1. 在首个 v1 发布窗口达到并维持：
   - `Coverage_effective >= 95%`
   - P0 接口覆盖率 100%
2. 最近 30 天内：
   - 覆盖接口自动化通过率 >= 99%
   - 因“CLI 不支持公开接口”导致的问题单占比持续下降（目标：< 5%）
3. 文档与体验指标：
   - 新用户 TTFS 中位数 <= 30 分钟
   - 文档相关咨询/工单量环比下降（目标：>= 30%）

---

## 10. 开发启动条件

仅当以下条件同时满足时启动开发：

- PRD 评审状态 = 通过
- v1 基线接口清单已冻结并归档
- 验收 checklist 已签字确认（产品/研发/测试）
